# Деплой

Схема повторяет рабочий проект District: один сервис отдаёт и API, и
собранный фронт, база — внешняя. Docker локально не нужен, собирает Render.

## Что попадает в образ

| Путь | Размер | Зачем |
|---|---|---|
| `server/dist` | ~1 МБ | API |
| `web/dist` | ~1 МБ | фронт, который раздаёт сервер |
| `storage/assets` | 188 МБ | файлы вложений для `/api/assets/:id` |
| `db/schema.sql` | 60 КБ | миграции при старте |
| `node_modules` (prod) | ~50 МБ | express, pg и прочее |

Не попадает: `content/` (232 МБ), `.pgdata` (677 МБ), профиль браузера
краула (161 МБ). Сервер читает `content/` только при импорте — в рантайме
все данные отдаются из Postgres.

## Порядок запуска

`docker/start.sh` → `node server/dist/scripts/migrate.js` (идемпотентно)
→ `node server/dist/index.js`.

Миграции гоняются на каждом старте намеренно: инстанс на Render
поднимается заново, а база общая, и схема должна соответствовать коду.

## Шаги

### 1. База данных

Render не даёт бесплатный Postgres, нужна внешняя. Подойдёт Neon
(бесплатно, 0.5 ГБ, без карты) — база занимает 76 МБ.

Нужна строка подключения вида:
`postgresql://user:pass@ep-xxx.region.neon.tech/baza?sslmode=require`

### 2. Заливка базы

Импорт выполняется с этой машины — `content/` лежит локально, клиентские
утилиты `psql`/`pg_dump` в системе отсутствуют.

```bash
DATABASE_URL='<строка от Neon>' npm run db:migrate
DATABASE_URL='<строка от Neon>' npm run import
```

### 3. Репозиторий

```bash
git remote add origin https://github.com/Soll-fx/<имя>.git
git push -u origin main
```

Репозиторий весит ~187 МБ: почти всё — это `storage/assets`. Файлы
включены намеренно, иначе вложения в статьях не отдаются.

### 4. Render

New → Blueprint → выбрать репозиторий. Render прочитает `render.yaml` и
создаст бесплатный веб-сервис с Dockerfile.

В `DATABASE_URL` вписать строку от Neon. Ставится вручную в панели,
в репозитории секретов нет.

## Ограничения бесплатного плана

- Сервис засыпает после 15 минут без запросов. Первый запрос после сна
  отвечает 30–60 секунд — для базы знаний это заметно.
- Файлы лежат внутри образа, поэтому переживают пересборку. Пользовательские
  загрузки — нет: они попадают в `storage/` контейнера и исчезают при
  следующем деплое.
- База на Neon своя бесплатная, у Render она не хранится.

## Как не давать сервису заснуть

`.github/workflows/keep-alive.yml` шлёт запрос на `/api/ping` каждые
10 минут, поэтому Render не усыпляет сервис.

**Пинговать `/api/ping`, а не `/api/health`.** Разница в лимитах:

| | Бесплатный лимит | Нужно на непрерывную работу |
|---|---|---|
| Render | 750 instance-часов/мес | 720 — помещается |
| Neon | 100 CU-часов/мес | 180 — **не помещается** |

`/api/health` ходит в базу. Если пинговать его, Neon не засыпает никогда:
compute 0.25 CU требует 180 CU-часов при лимите 100, и на 17-е сутки
Neon приостанавливает базу до начала следующего месяца — сайт лежит.

`/api/ping` базу не трогает, Neon продолжает засыпать через 5 минут и
расход CU-часов, а на первом реальном запросе просыпается за доли секунды.

Если workflow не помогает (расписание GitHub иногда задерживается при
нагрузке), надёжнее внешний пинг: UptimeRobot, бесплатно 50 проверок с
интервалом от 5 минут, или cron-job.org. Цель — `https://<домен>/api/ping`.

Второй постоянно работающий сервис Render в этом же аккаунте уже не
поместится: лимит общий на аккаунт.
